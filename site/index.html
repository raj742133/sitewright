Modules

Pick the pieces. Watch the site assemble.

Each module is a self-contained slice of the site with its own pages, API routes, database tables and settings. Choose one or all six; dependencies are added for you.

Pages

    API routes

      Landing page landing

      A public home page with an animated mark, a scroll-driven story with phone mock-ups, proof numbers, features, FAQ and a download card with a QR code.

      • Headline, steps and FAQ come from your config
      • Proof and feature sections stay off until you give real facts

      Sign in signin

      A shared-password gate in front of the private pages: signed cookie, constant-time compare, safe ?next= redirect, edge middleware.

      • API callers get 401, not a redirect page
      • Open-redirect attempts are ignored

      MFA accounts mfa

      Named accounts with password and authenticator-app codes. First-run setup, single-use invite links, lockout and an activity log.

      • TOTP ±1 step, a used code is refused
      • 5 wrong tries lock the account for 15 minutes

      Publishing publishing

      Upload a version, write notes in a rich editor, choose stable or testing, show it on the home page. Real APK parsing, or any file types you list.

      • Build numbers must rise; downloads are byte-identical
      • Testers get codes and see testing builds only
      needs: mfa (added automatically)

      Dashboard dashboard

      Stat cards, status chips, search and facet filters over a card grid of records, plus a detail page with files, line items and one-click status changes.

      • You name the statuses, labels and metrics
      • Fed by the ingest API, idempotent per record id
      needs: signin, api (added automatically)

      Under the hood

      A real backend, not a mock-up.

      The output is an ordinary Next.js 15 / React 19 / TypeScript project that you own. No runtime dependency on this skill.

      Layered sign-in

      Shared-password cookie, named MFA accounts, a bearer ingest token and per-tester codes — four separate layers, never merged.

      Direct-to-storage uploads

      Clients get short-lived signed URLs and PUT files straight to storage; the app only sees small JSON. Local, S3/R2 or Azure Blob.

      Idempotent ingest

      Re-sending the same record id updates it instead of duplicating it, so a phone that retries after losing signal does no harm.

      Postgres, with zero setup

      Runs on embedded Postgres (PGlite) out of the box and switches to your DATABASE_URL in production. Schema is created for you.

      Secure by default

      Scrypt password hashes, HMAC-signed cookies, constant-time compares, escaped config text, replay-proof authenticator codes.

      Your vocabulary

      Tell it a record is an “order”, a “matter” or a “loaf” and every label, heading and empty state follows.

      FAQ

      Questions people ask.

      Does the generated site depend on Sitewright?

      No. You get a normal Next.js project in a folder of your choice. Delete the skill and the site keeps working.

      Can I generate just one page, like only a landing page?

      Yes. Choose only landing and you get just that, with no database or sign-in. Dependencies are added only when a module needs them.

      Where does my data live?

      In your own database and storage. In development it is an embedded Postgres in a folder inside the project plus local files. For production you point DATABASE_URL at Postgres and choose local, S3/R2 or Azure Blob storage.

      Does it make up numbers or testimonials?

      No. Sections that need facts (proof numbers, feature lists, compatibility) are off until you give real content. The demo screenshots here use clearly fictional data.

      How secure is the sign-in?

      It follows common practice: scrypt hashes, signed cookies, authenticator codes that cannot be reused, lockout after repeated failures. It has not had an independent security audit, so review it before putting anything sensitive behind it.

      Where do the effects come from? Is this React Bits?

      No. Libraries like React Bits show what animated, copy-paste components can do, but their licence (MIT with the Commons Clause) does not allow redistributing them inside another package. These effects are written fresh for this kit, need no animation library, and are MIT licensed like the rest. The line figures are the exception: nineteen of them are Hairline by Lucas Marques, also MIT, included with its licence notice; three more are new here. Icons come from the open sets behind Iconify, found with better-icons (MIT), each under its own licence, which the generated site records.

      Do the effects slow the site down or hurt accessibility?

      They are built to avoid both: canvases pause off screen and in background tabs, pixel density is capped, pointer-follow effects are skipped on touch screens, and prefers-reduced-motion shows the final state at once. Headline animations keep the real text for screen readers. The verifier measures the pausing and checks the text.

      Why does verification need Playwright?

      Because a page that builds is not necessarily a page that works. The verifier signs in, enrols an authenticator, publishes a file and filters a list in a real browser, at phone width, and reports exactly what failed.

      Can I change the design afterwards?

      Yes. The colours are CSS variables at the top of globals.css, the logo is one file, and everything else is ordinary React you can edit. Re-running the generator into a fresh folder gives you a clean baseline to compare against.
